一、一页结论

外部材料共记录 5 项 ACL 2.0 问题。按代码根因合并后，实际对应 3 类问题： 部分 Proxy 请求没有正确加载权限规则、部分 Broker 管理请求没有生成权限判断所需的资源信息， 以及 gRPC 请求中的连接来源信息没有完全以服务端实际连接为准。 本期已完成这 3 类问题的代码修复和定向验证。

请求本身已经定义了 Topic 或 Group，但 Proxy 启动时没有装入对应 Header 映射，导致 ACL 不知道要检查哪个资源。

部分配置、查询和 ConsumerGroup 管理请求没有被转换成 Cluster、Topic 或 Group 权限判断。

外部提交现象

Header 注解与显式解析边界

对本次 DefaultAuthorizationContextBuilder 新增的 32 个 RequestCode 逐项核对 Header 注解。能够从 Header 的 @RocketMQResource 字段完整表达资源与动作的请求继续使用注解解析；资源位于 body、非通用 Header 或扩展字段， 请求本身代表 Cluster/类型化全量资源，或单个请求需要生成多个授权资源时，才保留 Builder 显式解析。 核对后，仅以下 3 个 RequestCode 存在“同码 Header 原有注解，但授权资源必须由 Builder 构造”的情况。

RequestCode 必须显式解析的原因 Header 调整
UPDATE_AND_CREATE_TOPIC_LIST Topic 列表位于 request body，Header 不携带具体 Topic 删除 CreateTopicListRequestHeader 的同码动作注解，并注明资源位于 body

第四封：gRPC 来源地址 Metadata 的所有权不明确

一句话说明： ACL 使用的来源地址必须来自服务端实际连接，不能沿用请求里已有的同名值； 修复后服务端会先清除旧值，再写入连接真实地址。

展开查看问题代码、修复代码和验证证据

原始主题： Security Vulnerability Report - Apache RocketMQ Access Control Bypass Vulnerability

外部提交现象

gRPC 请求 Metadata 与服务端连接属性使用相同的 remote/local address 键。 原实现采用“仅当 Header 不存在时写入”的方式，请求中已有同名值时， 服务端连接属性不会替换它，从而影响依赖来源地址的 ACL 判断。

代码根因

通用 put-if-absent 语义没有区分普通业务 Metadata 和服务端连接上下文。 参与 ACL 判断的连接信息需要由服务端统一确定，不能继承请求中已有的同名值。

public static <T> void putHeaderIfNotExist(
    Metadata headers, Metadata.Key<T> key, T value) {
    if (headers == null) {
        return;
    }
    if (!headers.containsKey(key) && value != null) {
        headers.put(key, value);
    }
}
修复前调用位置 · 基线 fbff64b31de7 · proxy/src/main/java/org/apache/rocketmq/proxy/grpc/interceptor/HeaderInterceptor.java:48

修复方式

  • 新增 GrpcUtils.putHeader，先清除同名值，再写入连接属性；
  • HeaderInterceptor 使用该方法写入由服务端连接派生的 REMOTE_ADDRESS，确保授权上下文中的来源地址取自服务端连接。

四、空授权上下文与老客户端兼容

ACL 做出判断，至少需要知道“谁在对哪个 Topic、ConsumerGroup 或 Cluster 做什么”。 服务端没有生成这些权限资源时，就属于“空授权上下文”。旧实现会直接继续处理； 本期改为默认拒绝，并为历史协议确实缺少资源字段的少量请求保留固定兼容。

01

修复后的三条处理规则

能识别资源

按 Topic、ConsumerGroup 或 Cluster 正常执行 ACL。

历史协议没有资源字段

只有命中代码内固定历史报文形态时才继续处理。

其他空上下文

未知、异常或本应有资源却没有解析出来的请求一律拒绝。

兼容边界： 兼容的是固定报文形态，不是客户端自报的版本号；兼容清单不能通过配置扩大。 ProducerGroup 只用于识别 Producer 生命周期报文，不作为 ACL 权限资源。 ClientID、消息标识、位点、事务状态等业务字段仍由原有业务逻辑判断，本次没有增加通用 checkFields 校验。
一期与二期： 空上下文默认拒绝、固定历史兼容、ProducerGroup 不作为资源等已经形成一期结论， 不进入二期重复修复。二期只处理仍缺少资源描述的 NotifyClientTerminationRequest、 THREAD_STACK_TRACE 和 VERIFY_MESSAGE_RESULT 协议字段及客户端升级。

问题本质

授权上下文用于表达“哪个用户对哪个 Topic、ConsumerGroup 或 Cluster 执行什么动作”。 原实现遇到空列表会直接返回，因而无法区分两种含义： 一种是 RequestCode、Header 或 body 的资源解析遗漏；另一种是历史客户端确实发送了不携带 ACL 资源的控制请求。 前者必须补齐资源并执行 ACL，后者需要在不扩大范围的前提下继续兼容。

public void evaluate(List<AuthorizationContext> contexts) {
    if (CollectionUtils.isEmpty(contexts)) {

统一处理流程

  1. Builder 先根据原始 Remoting/gRPC 请求构造授权上下文；
  2. 上下文非空时，对每个真实资源正常执行 ACL 策略；
  3. 上下文为空时，仅检查请求是否匹配代码内固定的历史报文形态；
  4. 命中后交由原有业务链路继续判断；不匹配固定形态或属于未知请求时一律拒绝。

8.1 身份可信与授权判定

目标： 服务端先得到可信身份，再依据真实用户状态、真实资源和确定的策略优先级做授权； 白名单和缓存不能改变这个顺序。

当前缺口 二期处理方式 兼容与验收
gRPC 身份字段仍可能沿用客户端预置值。 入口先清除客户端身份字段；认证成功后由服务端强制写入真实主体，长期改为服务端只读上下文。 不改变业务协议；验证不同账号签名和主体不能交叉使用，白名单请求不得发布未经认证的主体。
配置允许“只开授权、不认证”，认证和授权白名单也缺少包含关系约束。 配置加载和更新时强制“授权依赖认证”，并校验 authenticationWhitelist ⊆ authorizationWhitelist； Broker、Proxy Remoting、Proxy gRPC 再做请求级兜底。 非法组合启动或更新必须失败；合法历史配置保持原行为。
授权层可能检查临时 Subject 状态；同等精度规则中 DENY 优先级和 Comparator 契约不完整。 始终检查持久化 User 状态；修正 DENY 优先级及比较器的自反性、反对称性和输入顺序无关性。 覆盖 ENABLE、DISABLE、SUPER 和同精度 ALLOW/DENY 冲突，禁用账号不得继续使用旧允许结果。
Stateful 策略可能先命中缓存再判断白名单，用户禁用、密码轮换或 ACL 修改也只能等待 TTL。 白名单判断前置且不得读写受保护请求缓存；明确吊销生效 SLA，必要时引入 User/ACL 版本和多节点主动失效。 若产品接受 TTL，文档明确最长窗口；若要求立即吊销，验证单节点和多节点精确失效。
按 Offset 或事务标识找到真实消息后，部分处理链尚未校验声明 Topic 与真实逻辑 Topic 一致。 在 Query、EndTransaction 和对应管理处理链读取真实消息后做最小 Topic 一致性校验。 不改变现有事务检查 Header；声明资源与真实资源不一致时必须拒绝。

8.2 敏感信息与配置生命周期

目标： 密码和内部凭据只在确有必要的认证链内部使用，不从查询接口、命令行或日志向外扩散； 安全配置更新必须与运行时行为一致。

当前缺口 二期处理方式 兼容与验收
GET_USER/LIST_USER 仍可能返回密码字段。 LIST_USER 始终隐藏密码；GET_USER 仅本人或已认证 SUPER 可读取认证所需信息。 保留 Cluster Proxy 内部 SUPER 查询能力；普通用户不能读取其他账号密码。
Broker/Container 配置查询及 mqbroker -p 仍可能输出初始化密码和内部客户端凭据。 建立共用的敏感字段定义和安全视图，默认掩码；解析或脱敏失败时禁止回退原始内容。 普通字段继续可见；查询接口、命令行和错误分支均不得出现哑值原文。
Broker 可能在黑名单校验前记录完整 Properties，底层异常日志也可能拼接配置值。 统一为“先校验、再更新、只记录字段名”；异常日志不拼接 Properties，并恢复线程中断状态。 使用哑凭据捕获日志，验证成功、拒绝和异常路径都不泄露值。
通用远程更新不能同步重建认证授权运行时；白名单 setter 也不会让既有 Strategy 自动生效。 默认禁止通过通用配置接口热改全部 AuthConfig 字段。 白名单先明确“重启生效”还是“专用热更新”；只有确需热更新时才使用版本化校验和原子不可变快照。 不在请求路径重复解析配置；分别验证受控重启和专用原子更新，不允许配置值与实际行为不一致。

8.3 Container 与运行时隔离

目标： BrokerContainer 的控制端口必须受 ACL 保护；同一进程内的控制面和各子 Broker 必须拥有独立、可正确关闭和重建的认证授权运行时。

当前缺口 二期处理方式 兼容与验收
BrokerContainer 普通和 fast 两个控制端口尚未安装 Authentication/Authorization Pipeline。 建立独立的 container-control AuthConfig，两个端口安装同一套 Pipeline，覆盖 ADD、REMOVE、GET、UPDATE 控制操作。 旧版 Admin 工具继续通过既有签名 Hook 访问；验证两个端口的允许、拒绝和未签名场景。
Factory 使用可能为空或重复的 configName 作为进程级缓存 key，不同 Broker 可能复用同一运行时。 在 BrokerController 构造前生成包含 Container、Cluster、BrokerName、BrokerId 的稳定作用域 key，控制面与子 Broker 分离。 同名、不同 BrokerId、多 Container 场景不能共享用户、ACL 或缓存。
多个子 Broker 可能共用本地 ACL 目录，也缺少 canonical path 冲突检查。 每个 Local Provider 使用独立目录并拒绝路径冲突；External Provider 豁免，同时设计旧共享目录的数据归属和迁移。 升级不能静默切到空目录；验证文件锁、刷新线程、关闭和重建互不干扰。
未来引入运行时释放后，旧实例关闭可能影响新实例。 运行时句柄携带代次标识，锁内 compare-and-remove；禁止仅凭 configName 释放对象。 覆盖旧代关闭、新代存活、重复关闭和初始化失败回收。

8.4 迁移与主备数据一致性

目标： 迁移不能把非法旧权限扩大为允许，失败重试必须能补齐缺失 ACL； Master/Slave 切换前必须证明安全配置和 ACL 数据一致。

当前缺口 二期处理方式 兼容与验收
ACL 1.0 非法权限可能分别落入 ALLOW 和 Action.ALL 的宽松默认。 使用单一严格解析结果；只接受明确合法值，非法值只能 DENY、跳过或使严格模式失败。 覆盖大小写、空格、未知值和非法组合，任何异常输入都不能产生 ALLOW + ALL。
迁移发现 User 已存在时会跳过 ACL 创建，失败重试可能长期缺少 ACL。 拆分 ensureUser 和 ensureAcl 两个幂等阶段；匹配则补齐，冲突则报告并停止。 故障注入后重复执行应收敛到完整结果，不重复创建，也不静默覆盖冲突。
Master/Slave 的开关、白名单、Provider 和 User/ACL 数据没有上线或切主一致性门禁。 把配置和元数据版本、checksum 纳入发布及切主检查；不一致时阻断，不自动覆盖节点。 以真实主备环境验证升级、同步延迟、切主和回切，不能只依赖单元测试。

8.5 协议、网络与客户端演进

目标： 认证签名必须绑定真实请求，代理来源信息必须来自可信网络边界； 需要新增资源字段的协议通过新老客户端双轨升级。

当前缺口 二期处理方式 兼容与验收
gRPC 签名内容仍主要绑定时间，未完整绑定 RPC、Body、时间窗口和 nonce。 设计版本化 canonical request，绑定 RPC、AccessKey、timestamp、nonce 和 body digest；Unary 与 Streaming 分开定义。 兼容模式必须有观测和退出期限；修改 RPC/Body、过期时间或重复 nonce 均应失败。
PROXY protocol 缺少对真实 TCP peer 的可信代理 CIDR 校验。 部署层隔离端口；Remoting/gRPC 统一增加启用开关和 trusted proxy CIDR，未配置可信代理时 fail-closed。 使用真实网络路径验证可信代理、非可信直连、IPv4/IPv6 和关闭开关场景。
NameServer/Controller 尚未接入 ACL 2.0 Pipeline。 短期把网络隔离、mTLS 或网关设为部署前置条件；完整控制面资源和动作另行设计。 上线门禁必须检查端口暴露和访问路径；不能把网络隔离描述为已经完成代码授权。
空 Group 的 NotifyClientTerminationRequest、 THREAD_STACK_TRACE 和 VERIFY_MESSAGE_RESULT 尚无完整 ACL 资源载体。 新客户端增加资源或可信会话引用；服务端结合已认证连接、Settings、下发命令和 nonce 恢复真实资源。 旧客户端只在能力协商确认的迁移分支兼容；新客户端缺字段或校验不一致时不得降级。

三种报文的资源化方式

报文 资源来源 服务端校验 历史兼容
NotifyClientTerminationRequest 新客户端携带 Group/Topic 或服务端会话引用。 与已认证连接及服务端保存的 Settings/注册资源交叉校验，再生成 Group SUB 或 Topic PUB 上下文。 旧客户端空 Group 历史终止通知保留迁移兼容；携带资源的新客户端不得降级。
THREAD_STACK_TRACE 服务端下发命令时绑定目标客户端、资源和 nonce，客户端结果回显关联标识。 按服务端命令记录校验连接、命令类型、nonce 和资源归属，不单独信任客户端字段。 仅对能力协商确认的旧连接兼容，并设置命中观测和退出期限。
VERIFY_MESSAGE_RESULT 验证消息命令绑定 Topic、消息标识和 nonce，结果关联同一服务端命令。 从服务端命令记录恢复真实 Topic 并做权限和归属校验。 新能力连接缺字段、nonce 或会话不匹配时直接拒绝，不回落到旧兼容分支。
  • Telemetry 是双向流：服务端下发命令不作为入站 ACL 请求；客户端返回结果必须进入上述校验。
  • 新老协议通过能力协商和服务端会话状态区分，不能只相信客户端自报版本或 ClientType。
  • 兼容分支必须增加命中计数、客户端版本/连接维度观测和退出期限。

8.6 工程门禁与上线验收

目标： 以后新增接口、协议或配置字段时，测试必须主动暴露未定义授权语义和不一致状态， 不能依赖人工再次发现。

门禁 要求
接口完整性 建立集中式授权语义清单或完整性测试：每个生产 RequestCode/RPC 必须属于注解解析、显式解析、已知兼容或明确拒绝；新增未登记接口时测试直接失败。
版本兼容 服务端覆盖 Broker、Proxy、BrokerContainer；客户端覆盖新旧 Remoting/gRPC SDK 和 Admin 工具。
敏感信息 凭据、日志和配置输出测试只使用哑值，测试证据和报告中不得出现真实秘密。
真实环境 代理信任、主备切换、配置与 ACL 数据一致性必须有实际网络和切主证据，不能以静态代码检查代替。
分包验收 每个大类分别记录代码、单元测试、进程验证和兼容结论；未完成类别不能被“整体通过”覆盖。
