Proxy Cluster Mode Authorization Bypass via Uninitialized RequestHeaderRegistry
Summary
Apache RocketMQ's proxy component composes an AuthorizationPipeline on its remoting server but never calls RequestHeaderRegistry.getInstance().initialize() in cluster deployment mode. Because DefaultAuthorizationContextBuilder.buildContextByAnnotation() depends on the registry being populated to resolve @RocketMQAction-annotated header classes, it returns an empty context list for every request code that reaches the default branch of its switch statement. AuthorizationEvaluator.evaluate() silently passes on an empty list, bypassing all policy checks. Any authenticated low-privilege user connected to a proxy in cluster mode can consume messages from unauthorized topics (POP_MESSAGE), acknowledge and permanently delete those messages (ACK_MESSAGE), manipulate message visibility (CHANGE_MESSAGE_INVISIBLETIME), and enumerate consumer topology (GET_CONSUMER_CONNECTION_LIST) without holding the required ACL permissions.

Description
RequestHeaderRegistry Is Never Initialized in Proxy Cluster Mode
RequestHeaderRegistry is a singleton with an empty requestHeaderMap at construction time:

// RequestHeaderRegistry.java:29-63
public class RequestHeaderRegistry {
    private final Map<Integer, Class<? extends CommandCustomHeader>> requestHeaderMap = new HashMap<>();
    // map is empty until initialize() is called

    public void initialize() {
        Reflections reflections = new Reflections(new ConfigurationBuilder()
            .setUrls(ClasspathHelper.forPackage(PACKAGE_NAME))
            .setScanners(new SubTypesScanner(false)));
        Set<Class<? extends CommandCustomHeader>> classes = reflections.getSubTypesOf(CommandCustomHeader.class);
        classes.forEach(this::registerHeader);  // populates requestHeaderMap via @RocketMQAction scan
    }

    public Class<? extends CommandCustomHeader> getRequestHeader(int requestCode) {
        return this.requestHeaderMap.get(requestCode);  // returns null if map is empty
    }
initialize() is called exactly once in the entire codebase — in BrokerController.initialize():

// BrokerController.java:1307
RequestHeaderRegistry.getInstance().initialize();
In proxy cluster mode, ProxyStartup creates a ControllerManager or connects to an external controller, but does NOT instantiate a BrokerController. The BrokerController code path (which calls initialize()) is reached only in proxy local mode (embedded broker). In cluster mode — the standard production deployment — RequestHeaderRegistry.initialize() is never called and requestHeaderMap remains empty for the entire process lifetime.

The Proxy Wires Auth Pipelines But Omits the Registry Initialization That Makes Them Work
RemotingProtocolServer.createRequestPipeline() correctly composes authentication and authorization pipelines:

// RemotingProtocolServer.java:295-306
protected RequestPipeline createRequestPipeline() {
    ...
    pipeline = pipeline.pipe(new AuthorizationPipeline(authConfig, messagingProcessor))
                       .pipe(new AuthenticationPipeline(authConfig, messagingProcessor));
    return pipeline;
}
The proxy-specific AuthorizationPipeline delegates to AuthorizationFactory.newContexts(), which calls DefaultAuthorizationContextBuilder.build() — the same builder used by the broker. The broker works because it calls RequestHeaderRegistry.initialize() before any request is processed. The proxy cluster mode never does.

buildContextByAnnotation() Returns Empty Without Registry Initialization
DefaultAuthorizationContextBuilder.build() handles specific request codes with explicit switch cases (lines 194–324). For codes not listed — including POP_MESSAGE, ACK_MESSAGE, CHANGE_MESSAGE_INVISIBLETIME, GET_CONSUMER_CONNECTION_LIST, GET_MAX_OFFSET, GET_MIN_OFFSET, and SEARCH_OFFSET_BY_TIMESTAMP — control falls to the default branch:

// DefaultAuthorizationContextBuilder.java:325-327
default:
    result = buildContextByAnnotation(subject, command, sourceIp);
    break;
buildContextByAnnotation() looks up the header class from the registry:

// DefaultAuthorizationContextBuilder.java:347-350
Class<? extends CommandCustomHeader> clazz =
    this.requestHeaderRegistry.getRequestHeader(request.getCode());
if (clazz == null) {
    return result;  // returns empty ArrayList — no exception, no block
}

Fail-Open Design in AuthorizationEvaluator Completes the Bypass
// AuthorizationEvaluator.java:39-44
public void evaluate(List<AuthorizationContext> contexts) {
    if (CollectionUtils.isEmpty(contexts)) {
        return;  // NO exception — request proceeds unconditionally
    }
    contexts.forEach(this.authorizationStrategy::evaluate);
}
The empty list returned by buildContextByAnnotation() reaches evaluate(), which treats it as a signal to silently pass rather than deny — completing the bypass.

Inconsistency With Broker Confirms the Gap
The codebase's test for DefaultAuthorizationContextBuilder calls RequestHeaderRegistry.getInstance().initialize() explicitly at line 105 of DefaultAuthorizationContextBuilderTest.java, demonstrating that the test author understood initialization was required. The broker's production path (line 1307 of BrokerController.java) does the same. The proxy cluster startup path omits it.

Full Execution Chain
Attacker has valid low-privilege proxy credentials (any Normal-type user).

Attacker sends POP_MESSAGE (or any other affected code) to the proxy's remoting port with credentials in extFields.

AuthenticationPipeline runs — credentials are valid, passes.

AuthorizationPipeline.execute() calls DefaultAuthorizationContextBuilder.build().

extFields is non-empty (contains ACCESS_KEY) — early-return guard at line 182 is not triggered.

command.getCode() matches no explicit switch case → default branch → buildContextByAnnotation().

requestHeaderRegistry.getRequestHeader(code) returns null — registry never initialized.

Empty ArrayList returned.

AuthorizationEvaluator.evaluate([]) triggers early return — zero policy checks performed.

Request dispatched to PullMessageActivity.popMessage() / ConsumerManagerActivity.getConsumerConnectionList() / etc.

Handler executes against any topic or consumer group the attacker specifies, regardless of ACL rules.

Impact
Unauthorized message consumption: Any authenticated low-privilege user can consume messages from topics they have no ACL grant for, exposing message payload content across the entire cluster.

Message integrity loss: Consuming and acknowledging (ACK_MESSAGE) messages on behalf of another consumer causes those messages to be permanently deleted from the queue, disrupting legitimate consumers.

Consumer disruption via visibility manipulation: CHANGE_MESSAGE_INVISIBLETIME allows an attacker to push messages already in-flight to reappear immediately or to be hidden for extended periods, causing duplicate processing or indefinite message suppression.

Consumer topology reconnaissance: GET_CONSUMER_CONNECTION_LIST returns client IDs, network addresses, subscription tables, and consume-model settings for any named consumer group, providing detailed cluster topology information.

Silent — no error returned: Because the bypass is a silent pass (no exception, no log entry in the authorization layer), there is no indication in proxy logs that authorization was skipped for these codes.

Scope: Affects all proxy deployments in cluster mode when authorizationEnabled=true — which is specifically the configuration intended to enforce ACL controls.

Recommended Remediation
Option 1: Call RequestHeaderRegistry.initialize() in the proxy startup path (preferred — minimal change, fixes all affected codes)
Add the initialization call in RemotingProtocolServer or the proxy's startup sequence, before any request is handled:

// RemotingProtocolServer.java — init() or createRequestPipeline()
private void initAuthComponents() {
    if (authConfig != null && authConfig.isAuthorizationEnabled()) {
        RequestHeaderRegistry.getInstance().initialize();
    }
    // ... create pipelines
}
This is the lowest-effort fix — one line, consistent with what BrokerController.initialize() does, and protects all current and future codes that rely on the annotation-driven path.

Option 2: Move registry initialization into RequestHeaderRegistry.getInstance() (strongest fix — eliminates the initialization requirement)
Make the registry self-initializing on first access:

// RequestHeaderRegistry.java
private static class RequestHeaderRegistryHolder {
    private static final RequestHeaderRegistry INSTANCE = new RequestHeaderRegistry();
    static {
        INSTANCE.initialize();  // initialize at class-load time, before any caller can call getRequestHeader()
    }
}
This eliminates the requirement for callers to remember to call initialize() and prevents any future startup path from reproducing the same omission.

Option 3: Fail-Closed in AuthorizationEvaluator (defense-in-depth — fixes symptom for all callers)
Change the empty-context branch to deny rather than pass:

// AuthorizationEvaluator.java
public void evaluate(List<AuthorizationContext> contexts) {
    if (CollectionUtils.isEmpty(contexts)) {
        throw new AuthorizationException(
            "No authorization context resolved for request; access denied by default.");
    }
    contexts.forEach(this.authorizationStrategy::evaluate);
}
This is a defense-in-depth measure and should be applied alongside Option 1 or 2. On its own, it would block legitimate requests that intentionally resolve to an empty context (if any), so callers of the authorization pipeline for intentionally public/unauthenticated codes would need to be audited first.
